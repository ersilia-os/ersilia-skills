# Example audits

Two real reports, generated by this skill and committed verbatim so the output format can be
read and argued with without running anything. They are deliberately at opposite ends:

| Example | Repo | Result | Shows |
|---|---|---|---|
| [`eosquality-AUDIT.md`](eosquality-AUDIT.md) | `eosquality` (Package) | 1 blocker, 25 should-fix, 2 nice-to-have · 276 lines | The busy end. Every area populated, a blocker, the Evidence appendix, hand-verified Airtable checks, grouped skip reasons, Tier 2 gated shut. |
| [`eos-python-package-AUDIT.md`](eos-python-package-AUDIT.md) | `eos-python-package` (Template → Package profile) | 0 blockers, 8 should-fix, 4 nice-to-have · 120 lines | The quiet end. `✅ clean` areas, no Evidence appendix at all, template-suppressed checks, and a hand-added Airtable finding. |

Real output, not illustrations: if the format has a defect, it is visible here.

## What to look at, and what to push back on

**The three-part split.** *Verdict* is prose plus an area table. *Findings* says what is wrong
and where, one line each, **no fix text**. *Fix plan* says what to do. The same check ID appears
in both Findings and the Fix plan carrying different content — that separation is what keeps the
readable part near 120 lines rather than 206. Adding fix text back into Findings would undo it.

**The verdict is the only hand-written part.** Everything else is generated. It is the one thing
a reader is guaranteed to see, and the one thing that can be wrong in a way no test catches —
worth judging harshly.

**The `✅` / `—` distinction.** `✅ clean` means checks in that area ran and found nothing.
`—` means nothing was evaluated. An area that does not apply to the repo's type is omitted
entirely rather than marked either way. This broke twice during development, in both directions,
so it is the first thing to distrust.

**Readable length versus total.** The readable part (above `## Evidence`) is 76–122 lines across
the seven calibration repos. Totals run higher because the appendix scales with finding count;
it is inside `<details>`, so it renders as one toggle. `APPENDIX_ITEMS` in
`scripts/render_report.py` bounds it at 15 items per finding.

**The mechanical block is meant to be runnable.** It passes
`--config $SKILL/references/canonical-ruff.toml` on purpose: the findings were measured against
the canonical config, so a bare `ruff check --fix .` would use the repo's own drifted one and
fix something other than what the audit reported. Verified against `eosquality` with `--diff`:
"Would fix 17 errors", matching the reported 17× `I001`.

The `$SKILL` path in the block is this machine's, generated at render time. It is left as-is
rather than doctored, because a doctored example stops being real output.

## Regenerating these

```bash
cd skills/repository-auditing
python scripts/resolve_target.py eosquality --out /tmp/t.json
for c in docs code hygiene repo_meta practices; do
  python scripts/check_$c.py --target /tmp/t.json --type Package --status Todo \
    --out /tmp/ra_$c.json
done
python scripts/render_report.py --target /tmp/t.json \
  --findings /tmp/ra_*.json --verdict /tmp/verdict.txt \
  --type Package --type-source airtable --date $(date +%F) \
  --out examples/eosquality-AUDIT.md
```

The Airtable findings and the `--verified` entries in these examples were added by hand, as the
skill's Step 2 requires — Python cannot reach the Airtable MCP, so no script produces them.

## A note on the repeat-audit delta

Neither example shows one, because each was generated into a fresh path. Point `--out` at an
existing report to see it: the Verdict then opens with a line like

> Since the 2026-07-21 audit: **2 fixed**, 1 no longer checked, 1 new, 24 unchanged.

"No longer checked" is a separate bucket from "fixed" on purpose. A check that was gated out
this run says nothing about the repo, and conflating the two would have reported 8 Tier 2 items
as fixed the moment Tier 2 gating was introduced.
